# Showcase GIFs — animated usage

The static screenshots are generated by `scripts/showcase.py`, which drives the real app headlessly
over seeded logs into deterministic scenes (`docs/img/`, embedded in the README, smoke-tested by
`tests/test_showcase.py`). **Animated GIFs are the deferred follow-up**, built on the same machinery.

## Why generated, not hand-captured

The fixture basis (`tests/scenarios/`, `tests/helpers.py`) already drives the *real* app into precise
states via `App.run_test()` + `Pilot`, over seeded `runstate` logs with an injected clock. Rendering
showcase frames from it means no manual terminal, fully reproducible output, and visuals that cannot
drift from actual behavior — a broken screen fails the render. The capture primitives:
`app.export_screenshot()` → SVG (headless, no display), then SVG → PNG via `cairosvg`.

## Two routes for the animation

- **Frame sequences through Pilot (deterministic).** Capture one screenshot per step across a
  scripted interaction — `enter` → the drill-down streams a few log lines → `escape`; or `s` →
  confirm → `y` → the stop outcome — then assemble with `ffmpeg`/`imagemagick`. Use
  `held_writer_sqlite_run` so a tail visibly streams. Same determinism guarantee as the stills.
- **A terminal-native recorder (richer, less deterministic).** Charmbracelet **vhs**, or asciinema →
  **agg**, driving the real `runstate-tui <run.db>` CLI over a seeded db. Gives real motion — cursor,
  live ticks — at the cost of reproducibility. Pick per scene.

## Notes

- Keep the generator in-repo and CI-runnable (it exercises the real screens, so it doubles as a smoke
  test), but don't gate CI on pixel-diffing committed images — the snapshot suite already guards
  layout via `pytest-textual-snapshot`.
- A repo rename would churn these assets, so sequence any GIF work *after* a rename decision.
